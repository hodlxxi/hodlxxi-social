# Social preacceptance Ed25519 handoff V2: dormant compatibility contract

Status: **implemented only as dormant browser and pure server source; not wired,
not authority, and not deployable**.

This slice reproduces the externally owned Social mobile pre-enrollment V2
`register + initial` bytes while repairing the order in which a phone creates
its dedicated messaging authentication key. It does not accept a binding,
create an association, issue or consume a challenge, create a verification
statement, admit a request, create a session, or activate messaging.

The V2 modules are absent from browser entry, UI, BFF, composition and runtime
import graphs. Their exported runtime constants are false. There are no routes,
clients, feature flags, migrations, persistent server adapters or network
operations in this slice.

## Exact authority boundary

The browser may prepare public candidate evidence. The Social server may verify
the exact cryptographic transcript. Neither is acceptance or association
authority.

Only a future UBID transaction owner may durably accept a proposal or create an
association after independently authenticating a separately frozen V2
verification statement and locking/rechecking all required current state. That
statement contract, consumer and transaction owner do not exist here.

The following remain insufficient by themselves:

- a prepared browser key or signed-attempt record;
- a parsed pre-enrollment, approval event or acceptance wire;
- a comparison code, session, Full projection, candidate association link or
  cryptographic-verification result;
- local expiry, cancellation, a missing response or a caller boolean.

No V2 JWS bytes, producer or consumer are selected by this contract.

## Provisional browser key lifecycle

`web/messaging-device-ed25519-key-v2.mjs` is the sole owner of the dormant
version-1 to version-2 upgrade of the existing X25519 database
`hodlxxi-social-messaging-device-v1`. Version 2 retains the existing `device`
store and adds exactly one logically separate store,
`provisional-authentication-key-v2`. The upgrade from version 1 requires the
exact existing `device` topology and creates only the new empty store; it does
not read, rewrite, export or delete `device/current`. A fresh V2-owned database
creates those two stores. The old separate dormant database named
`hodlxxi-social-messaging-device-ed25519-key-v2` was never runtime-wired; this
slice neither uses, deletes nor reinterprets it. The accepted-binding Ed25519
V1 database and store remain separate and byte-identical.

The active X25519-only opener deliberately supplies no requested version. It
creates a genuinely fresh database at version 1 with only `device`, leaves an
existing version-1 database at version 1, and accepts an exact already-upgraded
version-2 topology while still accessing only `device`. Unknown versions or
any missing/unexpected store fail closed. Consequently, a cached copy of the
old module that still explicitly requests database version 1 receives
`VersionError` after V2 has upgraded the database and must be reloaded. Cache
and deployment sequencing is a controlled pre-activation rollout requirement,
not something this dormant source slice attempts to solve.

Records are keyed by exact `deviceId`. The only state is
`prepared-provisional`. Each immutable identity binds:

- the exact subject hint, device ID and request ID;
- the exact pending canonical X25519 register proposal and public key;
- the candidate binding ID and binding version 1;
- the binding-authorization content/digest and X25519 commitment;
- the raw 32-byte Ed25519 public key encoded as lowercase hex;
- a random record revision and the private Ed25519 `CryptoKey`;
- an optional immutable signing claim and optional exact signed-attempt wire.

The private key is generated by WebCrypto with `extractable=false` and only the
`sign` usage. IndexedDB structured clone is its sole persistence boundary. It
is never exported, serialized, returned in a public DTO, logged, rendered or
transmitted. Only the raw public key is exported. A stored record is reusable
only after every public binding matches and a domain-separated sign/verify
check proves that its private and public keys still form the same pair.

Every write uses a strict-durability transaction. Provisional creation and the
signing claim each use one readwrite transaction spanning `device` and
`provisional-authentication-key-v2`. In that transaction they freshly read and
validate the exact stored X25519 pending-register row and exact
subject/device/request/public-key/proposal identity, then run the exact
synchronous session guard immediately before `add` or `put`. No await,
Promise, crypto, network operation or caller-supplied authority value occurs
between that guard and the write request. Thus an X25519 transition and the V2
write have one IndexedDB serialization order. Creation uses `add`, so
concurrent tabs converge on the first writer. Signing-claim and signed-attempt
writes use the complete protected record identity and record revision as a
compare-and-swap identity. Signed-attempt persistence remains an evidence-only
single-store operation authenticated by the already durable claim; it does not
reacquire outward live authority. There is no deletion, promotion, ready,
accepted, active, current or rotation operation.

IndexedDB is local to one browser profile on one physical device. A laptop and
a phone do not share IndexedDB. This transaction owner proves atomicity only
inside that one browser/device; it is not cross-device transport, delivery,
runtime wiring, message activation or UBID association authority.

The same stable key signs only the existing Enrollment V2 phone-proof preimage.
There is no arbitrary signer, ordinary request-proof signer, encryption use or
participant/Nostr signing use.

## Explicit desktop approval and retry durability

`web/mobile-device-authorization-seams-v2.mjs` rechecks the exact desktop
session subject/revision and pending X25519 proposal across asynchronous
boundaries. It validates every active deadline immediately before NIP-07 and
again immediately after the signer returns.

Before acquiring the external provider, the browser durably claims the exact
signing attempt. That claim is deliberately not cleared in this slice. A crash
or ambiguous signer outcome therefore fails closed and cannot automatically or
silently reacquire the signer.

The provider public key must exactly equal both the authenticated session
subject and V2 pre-enrollment subject. The current session must also carry an
external `full` assertion; that assertion is necessary but does not itself
approve the key or grant authority. The seam invokes `signEvent` at most once,
locally verifies the returned private kind-27236 event, and releases its local
provider reference. It has no publish or relay interface.

After a fully validated event returns, the exact signed-attempt artifact is
strict-durability persisted before any dispatch-capable caller can receive it.
That evidence-only write authenticates exclusively against the already durable
exact signing claim and its exact device-ID/record-revision CAS record. It does
not reacquire the outward login, session revision or pending source and cannot
grant current authority. The outward seam separately rechecks cancellation,
all live context and deadlines after persistence and still fails closed if any
changed while the signer was open.
The artifact contains the exact outer wire, canonical event wire, event ID and
signature, request/pairing identities, public keys/commitments and all public
retry bytes. It contains no private key or raw pairing secret. Retries return
the identical artifact and never request a second signature.

Cancellation and local expiry prevent further outward use, but do not prove
that another authority failed to commit. Exact evidence and keys are retained.
This slice defines no irreversible authoritative rejection/cancellation and
therefore no deletion path.

## Frozen V2 bytes

`web/mobile-device-authorization-contract-v2.mjs` independently produces and
parses only the merged V2 vocabulary:

- pre-enrollment wire and domain-separated digest;
- V2 pairing/exchange commitments and pairing-possession HMAC;
- outer authorization envelope and digest;
- ordered private approval-event tags, NIP-01 event-ID input and event ID;
- BIP340-verified private approval event;
- acceptance-ID preimage, acceptance ID and candidate acceptance wire;
- immutable Social signed-attempt retry material.

The embedded X25519 binding authorization remains the unchanged V1
`register` claim. The pre-enrollment transition is exactly `initial`, from an
absent association at epoch 0 to candidate version/epoch 1 with no predecessor.
Rotate, adopt, revoke, reenroll and protocol autodetection are rejected.

All public parsers accept bounded printable-ASCII canonical wire strings.
Closed shapes and exact round trips reject missing, unknown, duplicate,
inherited, accessor, alternate-escaped, non-ASCII, unsafe-number and
noncanonical inputs. Raw pairing secret is accepted only by the isolated
commitment/HMAC boundary and is absent from all transcript/retry DTOs.

## Strict Social verifier

`src/server/messaging-device-preaccepted-enrollment-v2.mjs` accepts exactly one
canonical preaccepted-enrollment V2 wire string. It bounds and reparses the
complete nested graph before expensive cryptographic work. It independently
recomputes and compares:

- the pre-enrollment and outer authorization links/digests;
- the NIP-01 event ID and actual BIP340 approval signature;
- the acceptance-ID preimage/ID and candidate acceptance wire;
- the unchanged V1 verification context;
- Enrollment V2, its digest and exact phone-proof preimage;
- the V1 association-creation preimage/ID;
- the V2 verification-input digest and candidate association link.

Phone proof verification reuses the repository-owned Noble Ed25519 primitive
with canonical point/scalar, small-order and torsion checks and
`zip215:false`. WebCrypto, OpenSSL and shape-only verification are not
substitutes.

Success returns a frozen object registered in a module-private `WeakSet`.
Future consumers must pass that exact object through the exported brand-checking
projection; spreads, clones, proxies, prototype lookalikes and caller-built
objects fail. The projection expressly says `authority = not-granted`. Public
failure has one bounded non-sensitive message.

## Fixture and compatibility gate

The authoritative fixture is copied byte-for-byte as
`tests/fixtures/social_preacceptance_ed25519_handoff_v2.json`. It is exactly
32,998 bytes with SHA-256
`4f79dd0f24fd8ded4c2e4e3e644811dd42ca620d8c0e09aea177237dd5d199dc`.
It freezes every deterministic wire, digest, event ID, acceptance ID,
association ID and candidate link described above.

Existing V1 fixtures, serializers, digests, purposes and semantics are
unchanged. V1 and V2 are separate closed protocols: neither parser autodetects,
adapts or falls back to the other.

## Deferred work

Before any activation, separate reviewed increments must freeze and implement
the V2 verification-statement consumer/producer, durable UBID V2 acceptance,
acceptance-linked challenge issuance, and one atomic association owner with all
current session, Full, binding, acceptance, challenge and association rechecks.
Continuation identity, ordinary request proof, ciphertext transport, inbox,
self-read, UI and runtime activation remain deferred.

An expired or cancelled stored provisional record can intentionally block reuse
of the same `deviceId` because this slice has no authoritative delete or
replacement lifecycle. That is a hard blocker before runtime/UI activation
until UBID proves irreversible rejection/cancellation together with the exact
CAS identity; local expiry or cancellation alone is insufficient.

The source and synthetic IndexedDB regressions are not a native browser proof
of CryptoKey/versionchange behavior. Before staging, a real Chromium
version-1-to-version-2 rehearsal must preserve the populated non-extractable
X25519 key and V1 read/update behavior, exercise old-client `VersionError` and
controlled reload, and confirm strict two-store transaction behavior. This is
`REAL_BROWSER_UPGRADE_PREFLIGHT=REQUIRED_BEFORE_STAGING`. Cross-device
continuation and the irreversible lifecycle cleanup above are also unresolved,
so `DEPLOYMENT_READY=NO`.
