# HODLXXI Social contributor rules

- Work only in this repository and keep it independent from Universal-Bitcoin-Identity-Layer.
- Treat participant public keys as identity; never add passwords, KYC authority, server-side private-key custody, application/server signing with participant private keys, participant private-key uploads, or access to Bitcoin/Nostr/UBID private keys. A browser may request one explicit external NIP-07 signature only after the extension key exactly matches the authenticated session subject; Social must locally verify the returned event and must not retain the provider.
- Private-key persistence is prohibited except for two narrowly scoped V1.28 messaging requirements. The existing X25519 exception permits a dedicated, non-extractable browser-generated Social messaging device private CryptoKey to be persisted device-locally by IndexedDB structured clone, never exported or transmitted, and used only for HODLXXI Social internal messaging encryption. It retains the device key across browser restarts while the server holds only its public binding and does not permit Bitcoin/Nostr/UBID key reuse, authentication, general signing, or any server-held secret. Separately, the explicitly operator-authorized Ed25519 exception permits one dedicated, non-extractable browser-generated private CryptoKey per messaging device, persisted only through that approved browser storage boundary, never exported or transmitted, and used only for domain-separated exact messaging-device authentication and proof of possession. There is one current active Ed25519 authentication-key association per exact messaging device; controlled rotation may create a successor only during an atomic transition, and after rotation only the successor is current. The Ed25519 private CryptoKey and its record/schema/lifecycle remain separate from the X25519 encryption-key record/schema/lifecycle; neither key is derived from, aliased to, or substituted for the other. Its public key is bound through Enrollment V2; Social and UBID servers may hold only that public binding. The Ed25519 key is never used for encryption, participant/Nostr identity, ordinary Nostr event signing, Bitcoin, funds, covenant, wallet authority, or general-purpose signing. Any approval must come from the authorized external signer whose participant public key exactly matches both the authenticated session subject and the Enrollment V2 subject. Social must locally verify the returned approval event and exact subject match, and must release the signer/provider after that explicit approval. Full entitlement is necessary but insufficient; no different Full participant, sponsor, recipient, operator, administrator, or OAuth session may approve the association. This policy does not select or freeze the proof-profile identifier, serializer, preimage, or wire bytes; the future reviewed source implementation and fixed vectors must do so. Extractable-private-key persistence and private-key serialization to localStorage, sessionStorage, or JSON remain prohibited, as do private keys in DOM, URLs, logs, telemetry, or network payloads.
- Treat HODLXXI runtime/CRT as an external read-only authority. Social may consume assertions but must never grant Full or operator status.
- Keep social friendship separate from sponsor/covenant trust. Friendship is never proof of covenant trust.
- Keep V0 deterministic and offline: no databases, Redis, Bitcoin RPC, LND, relay requirement, deployment, or network-dependent tests.
- Preserve the non-claims in README.md and run the repository-local checks before handoff.
